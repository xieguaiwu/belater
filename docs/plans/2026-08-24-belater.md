# belater — DeepSeek 峰谷计费延迟执行器 Implementation Plan

> **For agentic workers:** 按本计划任务逐项实施。步骤用 checkbox（`- [ ]`）跟踪。

**Goal:** 构建 `belater`——Go 单二进制 CLI，把大型多 agent 任务（pi-agent / pi -p）排队到 DeepSeek 空闲时段自动执行，避开高峰计费（价格 2 倍）。

**Vision:** 新项目（belater 目录，空仓库）。短期目标 S1：v0.1.0 可用工具（队列 + 调度 + daemon + systemd 集成）。本计划属于 S1 全部。

**Architecture:** 纯标准库 Go 1.25，四层：`schedule`（峰谷窗口计算，含周末规则）→ `queue`（JSON 持久化 + flock）→ `runner`（sh -c 执行 + 日志 + 重试）→ `daemon`（调度循环）→ `cli`（子命令）。无第三方依赖。

**Tech Stack:** Go 1.25 标准库（encoding/json、time、os/exec、syscall.Flock、log/slog、flag）。无外部依赖。

**Spec:** 用户需求——"为 pi-agent 和 deepseek 的高峰计费机制专门设计一个 cli 工具，能够把要多 agent 大任务的工作放到高峰期之后自动执行"。

## Global Constraints

- Go 版本下限 1.25；只允许标准库，禁止第三方依赖
- 时区默认 Asia/Shanghai（DeepSeek 计费按北京时间）
- 峰谷规则（2026-08-23 生效，来源 api-docs.deepseek.com + IT之家）：
  - 周一至周五高峰：09:00-12:00、14:00-18:00（北京时间）
  - 周末（周六周日）全天空闲
  - 空闲价格 = 高峰 50%
- 所有窗口边界测试必须覆盖（09:00/12:00/14:00/18:00 整点切换 + 周末全天）
- 状态目录默认 `~/.config/belater/`，可用 `BELATER_STATE_DIR` 环境变量覆盖
- 用户可见文本简洁一致（ASD-STE100）：短句、一词一义、数字用数字

### Task 1: 项目骨架 + schedule 包（核心窗口逻辑）

**Files:**
- Create: `go.mod`（module belater，go 1.25）
- Create: `internal/schedule/window.go`
- Create: `internal/schedule/window_test.go`

**Interfaces:**
- Produces:
  - `type Kind int`（`KindPeak`、`KindOffPeak`）
  - `type Schedule struct { Location *time.Location; WeekdayPeaks [][2]int; WeekendAllOffPeak bool }`
  - `func DefaultSchedule() *Schedule` —— Asia/Shanghai，`[[540,720],[840,1080]]`（09:00-12:00、14:00-18:00），周末全天空闲
  - `func (s *Schedule) KindAt(t time.Time) Kind`
  - `func (s *Schedule) NextSwitch(t time.Time) time.Time` —— 下一个窗口边界（严格大于 t）
  - `func (s *Schedule) NextOffPeakStart(t time.Time) time.Time` —— 若 t 已是空闲返回 t；否则返回下一个空闲窗口起点
  - `func (s *Schedule) Multiplier(kind Kind) float64` —— 高峰 1.0、空闲 0.5
  - `func (s *Schedule) Describe(t time.Time) string` —— 如 "空闲时段 (0.5x)" / "高峰时段 (1.0x)"

**算法（窗口计算，必须精确）：**
- 按 `t.In(s.Location)` 取本地时刻，`weekday := t.Weekday()`
- `WeekendAllOffPeak` 且 weekday ∈ {Sat, Sun} → 全天 OffPeak
- 否则把本地时间转为"当日分钟数" `m := h*60+min`，与 WeekdayPeaks 区间比较（区间左闭右开）
- `NextSwitch`：遍历当日起点到终点（含跨日到下一天）的所有边界，取严格大于 t 的第一个；边界集合 = 每个 peak 的 start/end（若 WeekendAllOffPeak，周末无边界，边界从周六 00:00 到周一 09:00 之间不存在——注意周日 23:59:59 后下一个边界是周一 09:00）
- `NextOffPeakStart`：`KindAt(t)==KindOffPeak` → 返回 t；否则循环 `t = NextSwitch(t)` 直到 KindAt==OffPeak

**测试（window_test.go，表驱动）：**
1. 周五 10:00 → Peak；周五 08:59 → OffPeak；周五 12:00 → OffPeak；周五 13:59 → OffPeak；周五 14:00 → Peak；周五 18:00 → OffPeak
2. 周六 10:00 → OffPeak（周末规则）；周日 15:00 → OffPeak
3. 周一 09:00 整点 → Peak（左闭）；周一 12:00 整点 → OffPeak（右开）
4. NextSwitch(周五 10:00) = 周五 12:00；NextSwitch(周五 12:00) = 周五 14:00；NextSwitch(周五 18:00) = 周一 09:00（跨周末）
5. NextOffPeakStart(周五 10:30) = 周五 12:00；NextOffPeakStart(周五 16:00) = 周五 18:00；NextOffPeakStart(周五 19:00) = 周五 19:00（已在空闲）
6. Multiplier：Peak=1.0、OffPeak=0.5

### Task 2: queue 包（任务模型 + JSON 持久化）

**Files:**
- Create: `internal/queue/task.go`
- Create: `internal/queue/store.go`
- Create: `internal/queue/store_test.go`

**Interfaces:**
- Consumes: 无（独立）
- Produces:
  - `type Status string`：`Queued`、`Running`、`Done`、`Failed`、`Paused`、`Cancelled`
  - `type Task struct { ID string; Name string; Command string; Cwd string; Env []string; RunAt time.Time; Every string; MaxRuns int; Runs int; Retries int; TimeoutSec int; Status Status; CreatedAt time.Time; LastRun *time.Time; LastExit int }`（JSON tag 全小写下划线）
  - `func NewID() string` —— crypto/rand 8 位 hex
  - `type Store struct { Dir string; mu sync.Mutex }`
  - `func Open(dir string) (*Store, error)` —— 确保目录存在（0755）
  - `func (s *Store) Load() ([]*Task, error)` —— 读 queue.json，不存在返回空切片
  - `func (s *Store) Save(tasks []*Task) error` —— 原子写：queue.json.tmp + rename；写前 flock queue.lock（syscall.Flock LOCK_EX，阻塞），写后解锁
  - `func (s *Store) Add(t *Task) error`、`func (s *Store) Update(t *Task) error`（按 ID 替换）、`func (s *Store) Remove(id string) error`
  - `func (s *Store) LogPath(id string) string` —— `Dir/logs/<id>.log`；`EnsureLogsDir() error`

**规则：**
- 每次 mutation：Load → 修改 → Save（内存加锁，跨进程靠 flock 串行化；daemon 每次 tick 重新 Load）
- 状态非法值：Unknown 一律拒绝（保存前校验 Status ∈ 合法集合）

**测试（store_test.go）：**
1. 空目录 Open → Load 返回空
2. Add 两个任务 → Load 回读字段完全一致（含 time.Time 往返）
3. Update 替换同 ID；Remove 删除
4. 原子性：Save 后目录中无 .tmp 残留
5. 并发：两个 goroutine 各 Add 100 个，最终 Load 数量 = 200 且无损坏

### Task 4: daemon 包（调度循环 + 派发 + 崩溃恢复）

**Files:**
- Create: `internal/daemon/daemon.go`

**Interfaces:**
- Consumes: `schedule.Schedule`、`queue.Store`、`runner.Result`
- Produces:
  - `type Config struct { Store *queue.Store; Schedule *schedule.Schedule; Tick time.Duration; MaxParallel int; Once bool; LogWriter io.Writer }`
  - `func Run(ctx context.Context, cfg Config) error`
  - `func dispatchOnce(s *queue.Store, sch *schedule.Schedule, maxParallel int) error`（供 --once 与测试复用）

**调度语义（核心）：**
- 启动时恢复：所有 Status==Running 的任务 → 置回 Queued（RunAt 不变），记日志 "interrupted task recovered"
- tick 循环（默认 15s）：
  1. Load 队列
  2. 清理：Status==Done/Failed/Cancelled 且 CreatedAt 超过 7 天 → 删除（防队列膨胀）
  3. 派发：Status==Queued && RunAt ≤ now && 当前 Running 数 < MaxParallel → 置 Running，go Run
  4. 每个任务完成回调：ExitCode==0 → Done；否则重试逻辑：`Runs < Retries` → 置 Queued，RunAt = now + 30s×2^(Runs-1)（退避），Runs++；否则 Failed
  5. Every 逻辑：任务 Done 后若 Every != "" 且 (MaxRuns==0 || Runs < MaxRuns) → Runs++（Every 任务 Runs 计数含每次执行），RunAt = 下一次 Every 时刻（当天已过则次日），置 Queued
  6. Save
- `Once` 模式：执行一次 dispatch 后等待所有 Running 完成（上限 10 分钟），然后返回；用于 cron/systemd timer
- 优雅退出：ctx 取消（SIGINT/SIGTERM）→ 停止新派发，等待 Running 完成（上限 5 分钟），再退出
- `Every` 时刻计算：`nextEvery(t time.Time, every string) time.Time` —— every 格式 "HH:MM"；解析失败返回 t（任务下次 tick 仍不触发，记日志警告）

## 修订记录（v0.2.4，2026-08-29）

用户报「status 高峰时段显示明显落后」。核查后**规则未改**、窗口计算未改，改的是显示与现实的关系。以下三条是本项目的长期契约，后续任何改动都不得违反（README 开发节同步记载）：

1. **规则来源唯一**：峰谷窗口只依 https://api-docs.deepseek.com/zh-cn/quick_start/pricing 。2026-08-29 复核原文＝「高峰时段为北京时间周一至周五 9:00-12:00、14:00-18:00（其余为空闲时段）」，与 `DefaultSchedule()`（`[[540,720],[840,1080]]` + `WeekendAllOffPeak`）一致；逐分钟扫一周 10080 采样点对比独立参考实现 0 处不符。改规则须同改 `internal/schedule`、两个 README、本节约束段。
2. **判活契约**：「运行中」以持 `daemon.lock` 为准，但**无告警**还要求 `daemon.heartbeat`（pid/version/tick/last_tick_at）新鲜（grace = 3×tick+30s）且版本与本命令一致。只看锁会把卡死的循环、升级后未重启的旧版 daemon 报成健康。等待期（`--once` 收尾、优雅退出）必须继续 pulse，否则长任务会被误判为循环卡住。
3. **读写锁契约**：队列**读路径不得拿 `queue.lock`**。写方 `mutate` 持锁并以 tmp+rename 发布，读方加锁只会把 `status`/`list`/`results` 排到调度器后面（唯一能解释「命令慢十几秒」的代码路径）。
